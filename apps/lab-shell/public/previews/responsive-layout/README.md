# UI-LAB 통합 디자인 데모

현재 앱의 메뉴 의미를 유지하면서 공통 레이아웃을 검토하는 시안입니다.

- 실험실 `/lab` → 직접 조합한 UI 실험인 무한 스크롤 1개 `/lab/infinite-scroll`
  - 일반 실행, Virtuoso 실행 `/adapter-live`, 어댑터 코드 `/adapter-view`, 훅 해설 `/hook`
- 기능 비교 `/features` → 기능·구현 방식의 차이를 비교하는 4개 분류
  - React `/features/react`: 낙관적 업데이트·Activity·폼 액션·Effect Event·입력과 목록 갱신 실제 비교, Transition 예정
  - Next.js `/features/nextjs`: 서버·클라이언트 데이터 로딩, API·Server Actions 제출, 실제 Suspense 스트리밍 비교, PPR·Routing 예정
  - 라이브러리 `/features/libraries`: 실제 map·Virtuoso 목록 비교, fetch·TanStack Query 캐시 비교
  - 프레임워크 `/features/frameworks`: 네 프레임워크의 대시보드 서버 HTML·순차·동시 데이터 로딩 비교, 상품 상세 SSR 화면 시안
- 리포트 `/reports`, 버전업 로그 `/upgrades`, 공통 디자인 `/guide`

리포트 `/reports/dashboard-ssr`는 같은 고정 데이터를 사용한 네 프레임워크의 실제 SSR 반복 기록을 표시합니다. 조건·버전·콘텐츠 도착의 최소/중앙값/p95와 원본 JSON을 함께 제공합니다. `node scripts/collect-dashboard-report.mjs`로 production 서버에서 새 기록을 수집하며, 자세한 조건은 `docs/harness/results/dashboard-ssr.md`에 있습니다. 상품 상세 리포트는 아직 결과 미연결 상태입니다.

리포트의 `20회 분포`는 모든 표본을 같은 0ms 기준 축으로 표시합니다. 측정 회차 슬라이더는 마우스·터치·키보드로 사용할 수 있고, 선택한 회차의 네 값을 함께 강조합니다. `요약 수치`는 PC 표·모바일 카드로 전환됩니다. 데이터와 통계는 같은 원본 JSON을 사용합니다.

기존 구현·예정·화면 시안을 목록과 상세에 구분해 표시합니다. 예정 항목은 링크를 만들지 않습니다. 별도 프레임워크 앱의 SSR 구현과 측정 기록은 존재하지만, 상품 상세 SSR 시안에는 연결하지 않았습니다. RSC/CSC 비교는 같은 데이터를 브라우저 API 요청과 실제 async Server Component로 읽으며, 예시 번들 크기나 성능 점수를 표시하지 않습니다.

## 화면과 구현

`comparison-manifest.js`가 실제 비교의 제목·경로·범위·키워드를 한곳에 정의하고, `catalog-pages.js`와 `feature-pages.js`가 함께 사용합니다. `catalog-pages.js`는 목록과 기능 분류를 정의합니다. `routes.js`는 소속과 상위 경로를 등록하고, `preview.js`가 카테고리 선택·하위 메뉴·상위 경로·복귀 버튼을 일관되게 표시합니다. 본문은 같은 카테고리의 하위 페이지로 연결합니다. 옛 `/lab/list`, `/features/optimistic` 등의 공유 주소는 올바른 기능 비교 경로로 정규화합니다.

- `infinite-scroll-pages.js`: 기존 무한 스크롤 구현을 `/preview-embed/infinite-scroll/*`에서 재사용합니다. 현재 페이지 쿼리(`page`/`p`)를 부모 주소에 동기화해 새로고침·공유 시 복원합니다.
- `feature-pages.js`: React·Next.js·라이브러리 비교 12개를 `/preview-embed/features/*`에서, 서버 로딩과 네 프레임워크 대시보드 비교를 `/preview-embed/ssr/*`에서 실행합니다. 기존 비교 컴포넌트와 코드 하이라이트 구현은 그대로입니다. 임베드 링크 정리는 변경된 DOM만 살펴보므로 가상 목록 스크롤마다 문서 전체를 검색하지 않습니다.
- `upgrade-pages.js`: `/api/upgrade-logs`에서 원본 JSON의 목록을 읽고, `/preview-embed/upgrades/[id]`에서 기존 로그 상세와 파일별 코드 비교를 재사용합니다. 목록 새로고침·실패 시 재시도를 제공하며, 다른 메뉴에서 조작 중인 데모는 목록 응답 때문에 다시 렌더링하지 않습니다.
- `ssr-preview.js`: 별도 앱의 SSR 비교를 한곳에 배치하기 위한 시안입니다. 실행 결과나 성능 수치를 만들지 않습니다.

임베드 경로에서만 본앱 사이드바를 생략합니다. 원본 앱 주소와 기존 비교 컴포넌트는 유지하며, 임베드의 관련 링크는 같은 데모 카테고리 안으로 연결합니다. 색상·간격·반응형 기준은 공통 `style.css`를 따릅니다.

무한 스크롤은 상품 요청에 실패하면 기존 목록을 유지하고 자동 로딩을 멈춥니다. `다시 불러오기`는 실패한 페이지와 요청 방식(추가·교체)을 그대로 재시도합니다. 동시에 시작하는 요청은 하나로 제한하며, 화면을 떠난 뒤 도착한 응답은 반영하지 않습니다. 실행 임베드에서는 중복 제목을 생략하고 이동 버튼과 페이지 입력에 44px 높이를 확보합니다.

페이지 번호는 Enter 또는 입력란 밖으로 이동할 때 적용합니다. `처음·이전·마지막` 버튼으로 이동하면 편집 중인 번호를 취소하고 버튼의 목적지로 이동합니다. 일반 목록과 Virtuoso 목록은 같은 입력 규칙을 사용합니다.

무한 스크롤의 화면 자체가 15초 안에 도착하지 않거나 올바른 실행 문서가 아니면 `화면을 다시 불러오기`를 표시합니다. 현재 페이지 번호를 유지한 새 화면으로 재시도하며, 이전 화면의 늦은 응답은 반영하지 않습니다. 화면 안의 상품 요청 재시도와는 별도로 동작합니다.

실행 비교의 임베드는 콘텐츠 높이에 맞춰 커지고, 코드 패널만 독립적으로 스크롤합니다. 바깥 페이지에 있는 제목은 임베드 안에서 반복하지 않습니다. 초기 로딩 안내는 화면을 덮지 않아 서버 HTML이 도착하는 순서를 첫 진입에도 볼 수 있습니다. 낮은 PC 화면에서는 사이드 메뉴를 스크롤해 모든 하위 페이지에 접근합니다.

목록 카드는 PC·태블릿 2열, 휴대폰 1열을 기준으로 같은 제목·본문·하단 링크 간격을 사용합니다. 실험실과 기능 비교 모두 장식 이미지 없이 같은 카드 구조를 사용합니다. 같은 줄의 카드는 CSS subgrid로 제목과 하단 구분선을 맞추며, 긴 설명·버전은 자르지 않고 줄바꿈합니다. 카드 안쪽 여백은 24px(휴대폰 20px), 카드 사이 간격은 24px(휴대폰 16px), 다음 섹션은 32px(휴대폰 24px)입니다. 안내에는 `catalog-note`를 사용하며, 리포트의 상태와 링크도 고정된 열로 정렬합니다. 페이지 길이와 관계없이 마지막 콘텐츠와 푸터 사이를 32px(휴대폰 24px)로 유지합니다. 짧은 목록을 화면 높이만큼 늘려 빈 여백을 만들지 않습니다.

따뜻한 차콜 배경 위에 카드 면과 테두리를 한 단계 구분합니다. `data-family`의 작은 분류선과 메타 색으로 React·Next.js·라이브러리·프레임워크를 구분하며, 구현 여부는 별도의 글자 라벨로 표시합니다. 카드 hover와 키보드 focus는 같은 테두리·배경 변화를 사용하고 위치는 움직이지 않습니다. 상세 상태 안내와 작업 결과는 얇은 왼쪽 선과 짧은 문장으로 읽히게 합니다.

버전업 로그의 원본은 `docs/upgrade-logs/*.json`입니다. 새 기록은 별도 데모 데이터 작성 없이 목록과 상세에 나타납니다. 목록의 파일 수는 전후 코드가 포함된 고유 파일 수이며, 상세에서 파일을 선택하면 기존 코드 비교의 변경 줄 강조를 볼 수 있습니다. 테스트·검증 기록을 업그레이드 로그에 추가하지 않습니다.

경로와 분류 검사는 루트에서 `node --test scripts/design-preview.test.mjs`로 실행합니다.

신규 React 비교는 `useActionState`·`useFormStatus`, `useEffectEvent`를 실제로 사용합니다. 서버 스트리밍과 데이터 로딩의 조건·관찰 범위는 `docs/harness/scenarios/dashboard-ssr.md`에 기록합니다. 상세에서는 핵심 키워드와 관찰 방법을 공통 형식으로 표시합니다.

가상 목록은 실제 DOM 행 수를 관찰합니다. 양쪽에 같은 데이터·행 높이·뷰포트 높이를 적용하고, 코드 화면을 오가도 각각의 스크롤 위치를 유지합니다. 상세 범위는 `docs/harness/scenarios/list-virtualization.md`를 따릅니다.

캐시 비교는 같은 `/api/cache-demo`를 수동 fetch와 TanStack Query로 읽습니다. 700ms 고정 지연, 60초 fresh 캐시, 닫힘·항목 변경에 따른 취소와 재조회를 확인합니다. 코드 화면 전환도 데모를 다시 여는 동작이며 요청 시도 수에는 취소가 포함됩니다. 상세 범위는 `docs/harness/scenarios/query-cache.md`를 따릅니다.

`/features/frameworks/framework-dashboard`는 별도 앱 4개의 `/scenarios/dashboard-ssr`를 서버에서 요청합니다. 같은 fixture·지연의 HTML을 추출하고 공통 CSS로 표시합니다. 스크립트는 실행하지 않으므로 hydration이나 브라우저 렌더링 성능을 측정하지 않습니다. 상세 조건은 `docs/harness/scenarios/framework-dashboard-ssr.md`를 따릅니다.

순차·동시 데이터 로딩 비교는 작업 막대에 시간축을 표시합니다. 코드 탭에는 요청 순서와 함께 시간 기록·인공지연·막대 표시의 실제 파일을 포함해, 화면의 숫자가 어떻게 만들어졌는지 확인할 수 있습니다. 서버 작업 구간을 관찰하며 네트워크·브라우저 표시 시간은 포함하지 않습니다.

SSR 관찰 결과와 저장된 리포트는 브라우저에서 JSON 본문까지 최대 15초 기다린 뒤 재시도를 안내합니다. 메뉴 이동·조건 변경으로 취소한 요청은 오류로 표시하지 않습니다. 이 대기 제한은 측정 결과를 바꾸지 않습니다.

코드에서는 `서버 진입점 / 데이터 처리 / 화면 출력 / 오류 경계` 범위를 선택합니다. “수정하려면” 버튼으로 빈 상태 문구·지연 조건·404 처리에 관련된 파일을 찾을 수 있습니다. 각 역할의 실제 파일과 설명을 함께 표시하며, 하이라이트는 원본의 마커·코드 문장으로 연결합니다. 범위를 바꿔도 관찰 API를 재요청하지 않습니다. 네 앱 모두 선택한 지연 후 없는 팀을 404로 처리합니다. 오류 경계에서는 404 전달·예외 표시·복구 방법을 비교하며, 원본 앱의 복구 버튼을 실행하지는 않습니다.

`조건 링크 복사`로 선택한 두 프레임워크·팀·지연·코드 범위를 공유할 수 있습니다. 주소의 hash query를 iframe에 전달하고, 자식이 정규화한 조건을 같은 origin·현재 iframe·현재 메뉴인지 확인한 뒤 주소에 반영합니다. 조건 변경은 history 항목을 추가하지 않으며, 새로고침과 메뉴 이동 후 뒤로가기에서 조건을 복원합니다. 측정값은 재진입할 때 새로 수집합니다.

입력과 목록 갱신 비교는 같은 120행에 문구를 표시합니다. `useDeferredValue`와 `memo`가 입력과 목록의 반영 순서를 나누는 모습을 관찰하며, 인공 작업을 끈 조건도 제공합니다. 실제 속도 측정이나 검색 요청 예제가 아닙니다. 상세 범위는 `docs/harness/scenarios/deferred-value.md`를 따릅니다.

Activity 비교는 같은 메모 입력과 500ms interval을 사용합니다. 숨김·표시 시 입력 보존과 Effect 시작·정리 횟수를 관찰합니다. CPU 반복 계산이나 환산값을 표시하지 않으며, 코드에는 공유 probe의 실제 구현도 포함합니다. 상세 범위는 `docs/harness/scenarios/activity.md`를 따릅니다.

낙관적 업데이트는 각 요청과 실패 조건을 부모가 보관합니다. 코드 화면에서 만든 요청은 UI로 돌아오면 실행하고, 이미 시작한 요청의 확정 결과는 화면 전환 후에도 유지합니다. 세부 범위는 `docs/harness/scenarios/optimistic.md`를 따릅니다.

API 요청과 서버 액션 비교는 같은 이름 검증을 실제 서버에서 실행합니다. API의 JSON 요청과 Server Action의 함수 호출 연결을 비교하며, 800ms 지연과 서버 확인번호는 요청 관찰용입니다. 이름을 저장하지 않습니다. 자세한 범위는 `docs/harness/scenarios/server-actions.md`를 따릅니다.

요청 안에서 재사용 비교는 실제 Server Component에서 일반 함수와 React `cache()`를 실행합니다. 같은 팀·서로 다른 팀을 읽을 때 서버가 만든 실행 ID로 재사용을 확인하고, 새 응답에서는 ID가 달라지는지 살펴봅니다. 속도 순위나 영구 캐시를 측정하는 실험은 아닙니다. 자세한 범위는 `docs/harness/scenarios/request-cache.md`를 따릅니다.

Client Component와 첫 HTML 비교는 같은 카운터를 기본 사전 렌더링과 `dynamic(..., { ssr: false })`로 표시합니다. 실제 문서의 스크립트를 차단하면 서버 HTML만 남고, 허용하면 양쪽 버튼을 실행할 수 있습니다. 모드를 바꾸면 새 문서를 요청하며 카운터는 0부터 시작합니다. 문서 로드를 hydration 완료 시각으로 측정하지 않습니다. 자세한 범위는 `docs/harness/scenarios/client-prerender.md`를 따릅니다.
