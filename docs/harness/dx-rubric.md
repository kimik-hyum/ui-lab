# DX 스코어링 Rubric

DX 점수는 프레임워크의 절대 우열을 정하는 점수가 아닙니다.
동일 시나리오를 구현했을 때 코드 구조, 개념 수, 유지보수성을 비교하기 위한 기록입니다.
AI의 구현 성공률·재수정·사람 개입은 별도 [AI 작업 기록](ai-work-record-template.md)으로 평가합니다. DX 점수로 대신하지 않습니다.

## 점수 방식

- 각 항목은 1점에서 5점으로 평가합니다.
- 5점이 가장 좋고, 1점이 가장 나쁩니다.
- 총점은 가중 평균으로 계산합니다.
- 시나리오에 해당하지 않는 항목은 `N/A`로 두고 분모에서 제외합니다.
- 점수 옆에는 반드시 짧은 근거를 남깁니다.
- 가능하면 근거에 파일 수, 핵심 API 수, 주요 데이터 경계 수처럼 확인 가능한 단서를 함께 남깁니다.

## 가중치

| 항목 | 가중치 |
|---|---:|
| 프레임워크 관용구 적합성 | 20 |
| 데이터 흐름 명확성 | 15 |
| View 책임 분리 | 10 |
| 상태와 Pending 처리 | 10 |
| Mutation 및 동기화 난이도 | 10 |
| 파일 구조 탐색성 | 10 |
| 코드량과 개념 부담 | 10 |
| 타입 안정성과 계약 명확성 | 10 |
| 측정/디버깅 용이성 | 5 |

프레임워크 관용구와 데이터 흐름은 하네스 공정성에 직접 영향을 주므로 가중치를 조금 더 높게 둡니다.
측정/디버깅 용이성은 중요하지만 과하게 비중을 두면 앱 구현 자체보다 도구 친화성이 점수를 좌우할 수 있어 낮은 가중치로 둡니다.

## 평가 항목

### 1. 프레임워크 관용구 적합성

- 5점: 공식/일반 관용구에 잘 맞고 억지 추상화가 없습니다.
- 3점: 동작은 자연스럽지만 일부 구조가 애매합니다.
- 1점: 프레임워크 장점을 우회하거나 다른 프레임워크 구조를 억지로 이식했습니다.

### 2. 데이터 흐름 명확성

- 5점: route/data/query/mutation 경계가 코드만 봐도 분명합니다.
- 3점: 주요 흐름은 보이지만 일부 변환이나 캐시 책임이 흩어져 있습니다.
- 1점: 데이터 출처와 동기화 방식이 추적하기 어렵습니다.

### 3. View 책임 분리

- 5점: view는 표현과 UI 상태만 담당합니다.
- 3점: view에 일부 format/transform이 섞여 있지만 위험하지 않습니다.
- 1점: view가 API 호출, 캐시 정책, 도메인 로직까지 직접 품고 있습니다.

### 4. 상태와 Pending 처리

- 5점: loading, pending, empty, error 상태가 프레임워크 관용구로 명확합니다.
- 3점: 필수 상태는 있으나 중복 state나 애매한 fallback이 있습니다.
- 1점: 상태 처리가 누락되거나 서버 데이터가 local state로 불필요하게 복제됩니다.

### 5. Mutation 및 동기화 난이도

- 5점: mutation, invalidation, rollback, revalidation 책임이 명확합니다.
- 3점: 기본 mutation은 동작하지만 실패/rollback 근거가 약합니다.
- 1점: mutation 후 UI 동기화가 암묵적이거나 깨지기 쉽습니다.

### 6. 파일 구조 탐색성

- 5점: 시나리오 ID로 관련 파일을 빠르게 찾을 수 있습니다.
- 3점: 프레임워크 convention은 따르지만 관련 파일 추적에 약간의 탐색이 필요합니다.
- 1점: 기능 관련 파일이 흩어져 있고 책임 위치가 불명확합니다.

### 7. 코드량과 개념 부담

- 5점: 필요한 코드와 개념이 작고 반복 가능합니다.
- 3점: 약간의 boilerplate가 있지만 하네스에서 감당 가능합니다.
- 1점: 단순 기능 대비 파일/개념/설정이 과합니다.

### 8. 타입 안정성과 계약 명확성

- 5점: props, loader data, API response, mutation input/output 타입이 명확합니다.
- 3점: 핵심 타입은 있으나 일부 추론이나 캐스팅에 의존합니다.
- 1점: 주요 데이터가 암묵적이거나 `any`/불명확한 타입에 의존합니다.

### 9. 측정/디버깅 용이성

- 5점: 성능 측정 경계와 디버깅 지점이 코드 구조에서 바로 보입니다.
- 3점: 측정은 가능하지만 어떤 비용을 보고 있는지 코드/문서를 함께 봐야 합니다.
- 1점: SSR/API/Query/렌더링 비용이 섞여 결과 해석이 어렵습니다.

## 해석 규칙

- DX 점수는 성능 점수와 합산하지 않습니다.
- 단순 기능에서 boilerplate가 큰 프레임워크는 낮게 평가될 수 있습니다.
- 복잡한 기능에서 구조가 선명해지는 프레임워크는 높은 점수를 받을 수 있습니다.
- mutation이 없는 시나리오는 `Mutation 및 동기화 난이도`를 `N/A`로 둡니다.
- SSR-only 시나리오에서 client cache가 없는 것은 감점하지 않습니다.
- TanStack Query를 쓰지 않은 것이 감점이 되려면, 해당 시나리오의 측정 목적이 client cache였다는 근거가 있어야 합니다.
- 점수보다 근거가 중요합니다.
