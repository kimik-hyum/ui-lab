# 팀 대시보드 SSR 반복 기록

공유 화면의 `리포트 → 팀 대시보드 SSR`에서 네 프레임워크의 실제 반복 기록을 읽습니다. 원본은 `apps/lab-shell/public/previews/responsive-layout/reports/dashboard-ssr.json`이며, 화면에서 같은 JSON을 내려받을 수 있습니다.

`20회 분포`는 네 프레임워크의 개별 표본을 같은 0ms 기준 축에 표시합니다. 회차를 바꾸면 각 프레임워크의 해당 표본을 함께 강조합니다. 같은 회차 안에서도 요청은 순차 실행되므로 동시 요청 결과를 뜻하지 않습니다. `요약 수치`에서 최소·중앙값·p95와 본문 크기를 읽을 수 있습니다.

## 기록 조건

- 같은 `fixtures/dashboard-ssr.json`의 알파 팀을 사용합니다. 외부 DB는 사용하지 않으며, 지연 0ms에서는 타이머도 생성하지 않습니다.
- 네 앱 모두 production 서버의 blocking SSR입니다.
- 현재 앱의 공통 루트·QueryProvider를 포함한 응답입니다. 프레임워크 본체만 분리한 측정은 아니며, 루트·provider·스타일·빌드 설정도 출처 해시에 포함합니다.
- 프레임워크마다 워밍업 3회를 버리고 20회를 기록합니다. 요청은 하나씩 보내며 라운드마다 시작 프레임워크를 바꿉니다.
- lab-shell 관찰 서버가 프레임워크 서버의 HTML을 읽은 시간입니다. 브라우저 표시, hydration, LCP, 공유 터널의 전송 시간은 포함하지 않습니다.
- 1차 지표는 핵심 콘텐츠 완료 태그가 도착한 `contentReadyMs`입니다. 최소·중앙값·p95를 함께 표시합니다. 본문 크기는 압축된 네트워크 전송량이 아닙니다.
- 버전은 관찰 빌드의 설치 패키지 정보입니다. 기록 전에 실행 중인 앱의 소스·패키지와 일치하는지 확인합니다. 기록 당시 소스 파일의 SHA-256과 Git 기준도 JSON에 남깁니다.

환경은 수집 명령을 실행한 머신 기준입니다. 이 기록은 관찰 서버와 네 프레임워크 서버가 같은 머신의 loopback 주소에서 실행되는 조건입니다. 원격 origin을 사용하는 기록과 합치지 않습니다.

## 다시 기록하기

현재 소스로 빌드한 네 앱과 lab-shell을 먼저 실행합니다. 이 명령은 실행 중인 서버만 요청하며 빌드하거나 서버를 시작·종료하지 않습니다.

```sh
UI_LAB_BASE_URL=http://127.0.0.1:3003 \
node scripts/collect-dashboard-report.mjs
```

응답 오류, 다른 조건·버전, 잘못된 수치 또는 수집 중 소스 변경을 발견하면 기존 기록을 덮어쓰지 않습니다. 모든 표본을 확인한 뒤 결과 파일을 교체합니다. 공개 화면이 별도 빌드에서 실행 중이라면 새 기록을 포함해 빌드·배포해야 화면에 반영됩니다.

기존 `perf:ssr`의 문자열 첫 등장 시각과 이 관찰 API의 완료 태그 수신 시각은 정의가 다릅니다. 두 기록을 같은 통계로 합치지 않습니다. 단일 머신의 작은 시나리오이므로 전체 프레임워크의 성능 순위를 뜻하지 않습니다.

구현 조건은 [대시보드 SSR 시나리오](../scenarios/framework-dashboard-ssr.md), 해석 기준은 [성능 측정 방법론](../performance-methodology.md)을 따릅니다.
