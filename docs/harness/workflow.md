# 프레임워크 비교 작업

같은 사용자 시나리오를 최소 구현으로 비교합니다. 기능 수정·문서 정리에는 필요한 단계만 적용합니다.

## 1. 비교 조건 정의
- `scenario-card-template.md`에 목적, 대상 프레임워크, 경로, 입력·상태·조작, 데이터 원본, 허용 최적화를 적습니다.
- 브라우저 성능, SSR 응답, API 왕복, 클라이언트 캐시, DX, AI 작업 품질 중 평가할 축을 정합니다.
- 같은 fixture·지연·캐시·출력 포맷을 사용합니다. 조건이 다른 결과는 분리합니다.

## 2. 프레임워크별 구현
- `apps/AGENTS.md`와 대상 앱의 `AGENTS.md`를 읽습니다.
- 각 프레임워크의 공식 문서에서 route·data·mutation API를 확인하고 필요한 파일만 만듭니다.
- 같은 결과와 사용자 행동을 유지하되 파일 구조와 API는 각 프레임워크의 관용구를 따릅니다.
- 작업은 한 에이전트로도 완료할 수 있습니다. 병렬 위임은 필요한 독립 작업과 사용 권한이 있을 때만 선택합니다.
- SSR·API·Query의 비용과 streaming/blocking 조건을 코드와 시나리오에서 드러냅니다.

## 3. 검증
- 작업 중에는 대상 workspace의 lint와 관련 `scripts/*.test.mjs`를 실행합니다. 코드 변경 완료 전에는 루트 `yarn check`를 통과합니다.
- 변경한 route의 정상·빈 데이터·오류 중 필요한 경로를 확인합니다. SSR 비교는 응답 HTML의 핵심 콘텐츠와 status가 필수 조건입니다.
- SSR·캐시·초기 HTML을 바꾸면 현재 코드의 서버에서 `UI_LAB_BASE_URL=<주소> yarn test:runtime`을 실행합니다. 기본 `yarn test`는 서버 의존 검사를 포함하지 않습니다.
- 상호작용 변경은 브라우저에서 직접 재현합니다. URL 복원, 새로고침, 뒤로가기, 연속 입력, 요청 취소 등 영향받는 동작을 확인합니다.
- 코드 비교 변경은 실행/코드 전환, hover 토픽·하이라이트·대응 스크롤을 확인합니다.
- 실패한 검사를 숨기거나 검사 기준을 낮추지 않습니다. 원인과 남은 제약은 완료 보고에 남깁니다.

## 4. 측정과 기록
- 성능 측정을 요청받았다면 `performance-methodology.md`에 따라 production 환경에서 실행합니다. SSR의 content-ready와 브라우저 성능을 합산하지 않습니다.
- DX 비교는 `dx-rubric.md`의 근거 중심 평가를 사용합니다. 코드 구조 점수를 AI 작업 성공률로 해석하지 않습니다.
- AI 작업 품질을 비교할 때만 `ai-work-record-template.md`에 실행 조건과 관찰 결과를 남깁니다.
- 결과는 `docs/harness/results/`에 시나리오, 비교 조건, 실제 측정값, 해석상 제한을 짧게 기록합니다. 실행하지 않은 측정의 결과는 만들지 않습니다.
- 버전업 이력은 별도 스킬과 `docs/upgrade-logs/*.json` 형식을 따릅니다. 그 로그에는 검증 내역을 넣지 않습니다.
