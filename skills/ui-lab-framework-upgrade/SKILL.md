# UI-LAB 프레임워크 버전업

이 저장소의 프레임워크 업그레이드를 **공식 문서 확인 → 의존성 갱신 → 사용처 이전 → 검증 → 변경 로그 표시**까지 수행한다. 저장소 루트에서 작업하며, 루트와 해당 앱의 `AGENTS.md`를 함께 따른다.

## 1. 설치 상태와 공식 이전 지침 확인

- 기존 작업 변경 사항을 확인하고, 업그레이드 대상 앱과 패키지를 정한다. 사용자가 지정한 버전을 우선하며, 최신 버전을 요청했다면 실행 시점의 npm `latest` 안정 버전을 확인한다. 과거 대화의 버전 표를 재사용하지 않는다.
- `package.json`의 선언 범위, `yarn.lock`, 앱 위치에서 실제 해석되는 설치 버전을 구분해 변경 전 버전을 기록한다. 같은 패키지가 앱별로 다른 버전일 수 있다.
- 프레임워크의 공식 업그레이드 가이드, 릴리스 노트, 변경 API 문서를 읽는다. 여러 메이저를 건너뛰면 중간 메이저의 이전 지침도 확인한다. 문서 URL과 확인 날짜를 남긴다.
- Node, peer dependency, 타입 패키지, 빌드 플러그인, 배포 어댑터의 호환 범위를 조사해 함께 변경할 버전을 정한다. 호환되지 않으면 지원되는 조합이나 중간 업그레이드를 선택하고 이유를 설명한다.
- 문서의 필수 변경, 이 프로젝트에 해당하는 조건부 변경, 선택적 개선을 구분한다. 이전에 필요한 변경만 이번 작업에 포함한다.
- [로그 형식](references/upgrade-log-format.md)을 읽고 계획이 정해지면 템플릿으로 `in-progress` 기록을 만든다. 실제 버전업을 시작하지 않은 조사나 스킬 작성은 업그레이드 이력으로 만들지 않는다.
- `package.json` 수정·설치·codemod를 실행하기 전에 변경 대상의 현재 작업 파일을 임시 위치에 보관한다. 추가 사용처를 발견하면 그 파일도 수정 전에 확보한다. 미커밋 변경이 있을 수 있으므로 Git HEAD를 곧바로 변경 전 원본으로 쓰지 않는다.

## 2. package.json과 lockfile 갱신

- 대상 workspace의 `package.json`과 `yarn.lock`을 함께 갱신한다. 기존 exact/range 정책을 유지하되 공식 문서나 호환성 때문에 바꾸면 이유를 기록한다. lockfile을 수동으로 편집하거나 삭제하지 않는다.
- 함께 움직여야 하는 패키지를 확인한다. 예: 두 Next 앱의 Next와 `eslint-config-next`/명시한 SWC 패키지, React와 React DOM/타입, React Router의 `@react-router/*`, SvelteKit과 Svelte/Vite 플러그인/Vite/adapter, Nuxt와 Vue/`vue-tsc`.
- Nuxt가 관리하는 Nitro/Vite 같은 간접 의존성은 먼저 Nuxt의 지원 범위를 확인한다. 최신 버전을 강제로 넣기 위한 `resolutions`, peer 검사 무시, 타입 검사 해제를 기본 해결책으로 삼지 않는다.
- 저장소에 고정된 Yarn을 사용해 필요한 설치를 수행하고 실제 해석 버전을 다시 확인한다. Node 요구사항이 바뀌면 `.nvmrc`, 루트 `engines`, Docker 및 관련 실행 안내를 함께 맞춘다.

## 3. 문서에 따라 코드 사용처 이전

- 문서에서 변경된 API, import, 설정 키, route convention을 `rg`로 찾아 실제 사용하는 곳에 적용한다. 검색 범위에 앱 코드뿐 아니라 비교 데모, 코드 예제, 성능 스크립트, 관련 문서를 포함한다.
- 공식 codemod가 적합하면 대상과 변환 내용을 확인한 뒤 사용하고 diff를 검토한다. 사용하지 않는 API나 이미 호환되는 코드는 억지로 수정하지 않는다.
- 각 프레임워크의 서버 데이터 경계와 오류 처리 관용구를 유지한다. 비교 시나리오의 fixture, 데이터 원본, 표시 포맷, 캐시 정책, streaming/blocking 조건을 바꾸면 로그에 명시한다.
- 버전업으로 비교 페이지의 예제나 설명이 달라지면 실제 데모와 설명을 함께 갱신한다. `[cmp:<key>:start/end]` 앵커, fallback 라인, hover 토픽 연결을 확인한다. 신규 기능 비교를 추가할 때는 `ComparisonTemplate`을 사용한다.
- 각 변경에 대해 공식 문서 근거와 사용처, 변경 이유, 관찰 가능한 전후 동작을 기록한다. 문서 검토 결과 사용처 변경이 불필요했다면 확인 범위와 그 이유를 남긴다.
- README, 앱별 `AGENTS.md`, 버전 카탈로그와 배포 설정에 이전 버전·동작을 전제로 한 안내가 있으면 영향받는 항목을 함께 갱신한다.

## 4. 검증

- 루트의 `yarn lint`, `yarn build`를 실행한다. 실패하면 이번 변경 때문인지 환경 때문인지 구분해 수정하고, 해결하지 못한 경우 대화에서 알린다. 실행 결과는 버전업 로그에 저장하지 않는다.
- 바뀐 동작에 맞춰 영향받는 앱의 route, 주요 상호작용, SSR 콘텐츠, 필요한 오류 경로를 확인한다. 비교 코드가 바뀌면 hover 토픽/라인 매칭을 브라우저에서 확인한다.
- SSR 또는 성능 비교 조건이 바뀌면 관련 시나리오의 측정 방법에 따라 필요한 smoke/performance 검증을 추가한다. Supabase 환경 등 선행 조건이 없어 진행하지 못한 경우 대화에서 알리고, 시도·미실행 내역은 로그에 남기지 않는다.
- 이전 성능 결과를 새 버전의 결과로 재표기하지 않는다. 재측정한 경우에만 실행 환경·조건·결과 경로와 함께 갱신한다. streaming 프레임워크 간 비교는 `content-ready` 기준을 유지한다.

## 5. UI-LAB에 변경 로그 기록

- [로그 형식](references/upgrade-log-format.md)에 따라 변경 코드·버전, 변경 이유와 공식 문서 권고안만 남긴다. 테스트 결과, 검증 시도·계획, 미실행 항목, 환경 장애 메모는 저장하지 않는다. 작업 단위별 로그를 보존하고, 같은 작업을 재개할 때는 기존 기록을 갱신한다.
- 새 로그의 각 코드 변경에는 `changes[].files`로 실제 파일별 전후 발췌와 원본 시작 줄을 고정 저장한다. 변경 전은 확보한 작업 원본, 변경 후는 최종 파일에서 추출하고, 해당 버전업의 변경 구간만 담는다. 현재 파일이나 Git 상태를 런타임에 읽어 과거 이력을 바꾸지 않는다. 요약 문장만 남겨 코드 비교를 생략하지 않는다.
- 기존 로그 UI를 그대로 사용해 **파일 선택 → 전후 코드 비교 → 삭제·추가 줄 하이라이트 및 hover 대응**을 제공한다. 같은 변경 카드에 짧은 `reason`, 공식 `recommendation`, 근거 `sourceIds`를 연결한다. 컴포넌트 재사용과 자동 diff 규칙은 [화면 계약](references/upgrade-log-format.md#화면-계약)을 따른다.
- 로그의 원본은 `docs/upgrade-logs/*.json`이다. UI 표시용 배열이나 Markdown에 내용을 중복 저장하지 않는다.
- 기록은 핵심 위주로 읽기 쉽게 쓴다. 요약은 한 문장, 변경 이유와 문서 지침은 짧게 적는다. 호환성 때문에 선택한 버전의 이유는 관련 코드 변경에 합친다. 문서의 권고·필수 요구와 프로젝트 자체 판단을 구분한다. 작성 기준은 로그 형식을 따른다.
- 첫 실제 버전업에서 메뉴가 없다면 `apps/lab-shell`의 Sidebar에 **버전업 로그** 링크와 `/upgrade-logs`, `/upgrade-logs/[slug]` 화면을 구현한다. 이후 로그 파일 추가만으로 목록과 상세가 나타나게 한다. 구현 계약은 로그 형식 문서를 따른다.
- `yarn test:upgrade-logs`로 새 기록의 데이터 계약을 확인하고, 발췌와 시작 줄을 변경 전 원본·최종 파일에 대조한다. 화면에서 파일 선택, 전후 코드, 삭제·추가 강조와 hover 대응, 변경 이유·문서 링크를 확인한다. 새 파일·삭제 파일이 있으면 빈 쪽 안내도 확인한다. 로그 UI를 추가하거나 바꿨다면 그 변경까지 포함해 린트와 빌드를 검증한다. 이 확인 내역도 로그에 저장하지 않는다.
- 필수 검증을 통과한 작업만 `completed`로 기록한다. 진행 불가면 `blocked`, 변경을 되돌렸으면 `rolled-back`으로 남기고 상태를 표시하되 실행 과정은 대화에서 설명한다.

## 완료 보고

변경 전후 실제 버전, 주요 이전 내용과 UI 로그 주소를 한국어로 보고한다. 작업 완료에 영향을 주는 문제가 있으면 대화에서 설명한다. 커밋·푸시·PR·배포는 사용자가 요청한 범위에 따라 별도로 처리한다.
